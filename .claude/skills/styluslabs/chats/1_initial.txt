● Yes, this is doable, and the protocol makes it fairly easy. You don't have to
  change the app at all. The agent can join as another whiteboard user, so every
  human connected sees its strokes appear live.

  How the whiteboard sync works (from scribblesync.cpp / scribbleapp.cpp)

  The comment at syncscribble/scribblesync.cpp:9 says the server is "trivial: 
  just rebroadcasts everything it receives." There are two ports:

  1. HTTP API on :7000 (one request per connection, Cookie: session=)
  - GET /v1/auth?user=U&timestamp=T&signature=S, where pw = 
    md5("styluslabs"+password) and S = md5(pw + T). The reply sets a session
    cookie.
  - GET /v1/createswb?name=… or /v1/openswb?name=… returns XML with name, token,
    user, and optionally rxonly.

  2. Sync stream on TCP :7001
  - Send: /start?version=1&user=U&document=D&token=K&uuid=<random>&offset=0\n
  - Receive: a stream of <undo uuid=… user=… pagenum=…> …items… </undo>\n
    blocks. These are sometimes gzipped; look for the \x1F\x8B magic. With
    offset=0 the server replays the whole history, so a new client can rebuild
    the full canvas.
  - Send: /data?length=N\n followed by N bytes of <undo> blocks.

  Item types:
  - Pages: addpage (full page SVG), delpage, pagechanged
  - Strokes: addstroke strokeuuid= pagenum= nextstrokeuuid= wrapping an SVG
    <path>, plus delstroke, translate, transform, strokechanged
  - Other: viewbox, connect, disconnect

  Everything is SVG, which suits an agent well: it can read the canvas as text
  or as a rendered image.

  Suggested design

  A small Python daemon that acts as a headless whiteboard client, with an MCP
  server on top:

  - Daemon: keeps the :7001 socket open, applies incoming items to an in-memory
    model ({page: {uuid: svg_element}}), and sends the agent's edits. This needs
    to be a long-running process, so it fits your "run in the background on the
    desktop" idea. A thin MCP layer (stdio, or HTTP if several agents share it)
    talks to the daemon.
  - Tools:
    - get_canvas(page) returns a PNG rendered with resvg or cairosvg so the
      model can see it, plus optionally the raw SVG.
    - draw_path(page, points | svg_d, color, width) sends an addstroke with
      nextstrokeuuid=0, which appends on top.
    - write_text(page, x, y, text): Write only stores ink strokes, so text would
      be drawn with a single-stroke Hershey font.
    - erase(uuids), move(uuids, dx, dy)
    - list_users(), wait_for_changes(timeout) so the agent can react when
      someone draws.

  Gotchas

  - The server isn't in this repo. Only the client is here. Which server are you
    running, Stylus Labs' or your own? Its auth and history replay behaviour
    decide how much of the above is needed.
  - Stroke format: I'd capture a real session first (e.g. tcpdump or a logging
    proxy on :7001) to copy exactly which <path> attributes Write sends. Then
    agent strokes will look and behave like native ones for selecting, erasing
    and so on.
  - Undo: the C++ client does tricky undo/redo reconciliation (sendHist). The
    agent should only ever append items and never "undo", which avoids all of
    that.
  - Read-only mode: lecture-mode boards (rxonly) only let the creator send
    changes.
  - Auth is weak (MD5, plaintext HTTP), so keep the server on the LAN or behind
    a tunnel.

  Want me to build it? I'd start with a protocol-capture/replay script to pin
  down the stroke format, then the daemon and MCP tools.

  Why two sockets

  They aren't open at the same time. The app uses them in two separate phases:

  1. Port 7000, short-lived HTTP. syncAPICall sends Connection: close, so each
     request is one connection. It's used for /v1/auth, which returns a session
     cookie, and for /v1/createswb or /v1/openswb, which return the document
     name and a token.
  2. Port 7001, one long-lived raw TCP stream. The first line /start?...&token=K
     presents that token. After that, both directions use the same socket: you
     send with /data?length=N\n + payload, and you receive the <undo> blocks.

  So the live session already runs over a single, full-duplex socket. Port 7000
  is effectively a login step that hands out a token. I'd guess the split exists
  so the rebroadcast server can stay very simple and never parse HTTP or check
  passwords.

  Can it be WSS on one socket?

  For the agent's side, yes. That's up to you, because your daemon sits in
  between. The MCP or daemon can expose whatever it likes, and the daemon makes
  the 7000/7001 connections locally on the server machine. If the daemon runs on
  the same desktop as the server, the plaintext legs stay on localhost.

  For the Write app itself, no, unless you change its code. The ports "7000" and
  "7001" are hardcoded (scribbleapp.cpp:2626, scribblesync.cpp:85), and
  ulib/unet only does raw TCP. There is no WebSocket or TLS support anywhere,
  including in the wasm build.

  If the goal is encryption and a single port for remote human clients too, you
  have three options:

  - Tunnel (easiest, no code changes): put the server behind WireGuard or
    Tailscale, or use ssh -L 7000:… -L 7001:…. Clients connect to localhost, and
    the traffic is encrypted.
  - Your own server: the protocol is small enough to reimplement over a single
    wss endpoint. Auth would go in the upgrade request
    (wss://host/swb/<doc>?user=…&sig=…), and each WS message would be one <undo>
    block. WS framing would also replace the /data?length= framing. You'd still
    need a small TCP adapter for unmodified Write clients, or a patch to Write
    to speak WS.
  - WS→TCP bridge (e.g. websockify): this works for 7001, but you'd still need
    the separate auth call, so it doesn't get you down to one socket.

  My recommendation: run the agent daemon on the server desktop and talk to
  7000/7001 over localhost. Expose MCP over stdio for local agents, or over
  HTTPS/WSS if remote agents need it. Use a tunnel for remote humans. That gives
  you encryption without touching the C++ side.

● They're ephemeral on the server side. Persistence only exists in each
  participant's own local copy.

  Server (whiteboard.js)
  - A whiteboard is just an in-memory string, wb.history, that accumulates every
    <undo> block anyone has sent. It is never written to disk.
  - It's deleted del-delay seconds after the last client leaves, and everything
    is lost if the server restarts.
  - History is never compacted. Every joiner replays all of it, including
    strokes that were later erased.

  Client (Write)
  - Create Whiteboard shares whatever document you have open. The creator pushes
    all its current pages, and the document stays tied to your local file. You
    save it like any notebook.
  - Open Whiteboard auto-saves the incoming board as <currFolder>/<title>.svg
    (scribbleapp.cpp doSharedDoc). From then on it's a normal local notebook
    that keeps receiving live edits.
  - So everyone ends up with their own copy on disk. Nothing ties those copies
    back together once the session ends. Each session is a new board seeded from
    someone's current file.

  For a persistent notebook shared with an agent

  I'd make the agent daemon the owner of the notebook, not the server or your
  app:

  1. On startup the daemon loads ~/notebooks/foo.svg. It creates board foo as
     the master and pushes every page with addpage.
  2. It applies every incoming item to its in-memory model and writes the SVG
     back to disk on a debounce. That disk file is the source of truth.
  3. You run Open Whiteboard you@10.126.202.132/foo whenever you want to work on
     it. You see the current state, and edits flow both ways live.
  4. When the daemon restarts, it re-creates the board from disk. That also
     fixes the history growth, because the new board starts from a compacted
     copy.

  The agent's MCP tools then read and modify the daemon's model directly, with
  no extra network hop.

  Caveats
  - Many notebooks: one board per notebook is fine for the daemon. However,
    Write has no way to browse boards, so you'd type the ID each time. The
    daemon could create boards lazily for every file in a folder.
  - Your local copy goes stale: the auto-saved copy from Open Whiteboard drifts
    away from the daemon's copy between sessions. Treat it as a cache. Don't
    edit it offline, because nothing would merge those edits back.
  - Simpler fallback with no live sync: the agent edits the .svg files directly,
    and you reopen them in Write, synced with something like Syncthing. That
    only works if you never edit the same notebook at the same time as the
    agent. It's fine for "leave me notes overnight", not for drawing together.

  I'd do the daemon. It's the same headless client we talked about, plus
  load/save and master mode. Want me to start on it once Node is installed and
  you've tried a session by hand?

● Neither, actually. Write already detects outside edits and reloads the file.
  Your situation fits it well.

  What Write does now (checkExtModified, scribbleapp.cpp:1842, setting
  warnExtModified is on by default):
  - It compares the file's modified time when the window regains focus, then
    every 5 s while the window stays focused. The timer stops when you switch
    away.
  - No unsaved local changes: it reloads silently, apart from a "Document
    reloaded" popup.
  - Unsaved local changes: it shows a conflict dialog with Keep Both / Discard 
    Other / Discard Current. Saving does the same check first (doSave,
    line 1904), so your save never silently overwrites the outside edit.
  - It doesn't run on iOS or in the wasm build.

  Rough edges for an agent writing often:
  - The "Document reloaded" popup shows on every reload. That gets annoying
    quickly. It's a one-line patch to remove it.
  - A reload is a full openDocument. You lose undo history, and the view jumps
    to whatever page and scroll position is stored in the file. The agent should
    keep the file's saved position as it is, or the patch could keep the
    current view.
  - The agent must write atomically: write a temp file, then rename it.
    Otherwise Write may read a half-written file.
  - If the modified time only has 1‑second resolution, two writes in the same
    second could be missed. I'd check that before relying on it.
  - You still have to save (Ctrl+S) before the agent sees your strokes.
    Otherwise the agent's write runs into your unsaved changes and you get the
    conflict dialog.

  What this means for the plan: for taking turns, a file-based setup works
  almost as-is and is much simpler than the whiteboard daemon:
  1. You draw and save.
  2. The agent reads the SVG, edits it, and writes it back atomically. It should
     check the modified time first and back off if the file changed in between.
  3. Write reloads within about 5 s.

  Notebooks persist automatically, and all of them work, not just one. I'd keep
  the whiteboard approach in reserve in case you want live drawing at the same
  moment. The worthwhile patch to Write is a silent reload that keeps your
  current view, possibly behind a config flag.

  Want me to try the file approach first? I'd check the modified-time resolution
  and the stroke format in a real notebook, then sketch the read/write tools.
